# Отчёт по восстановлению модели процесса (Process Discovery)

## 1. Инструменты и методология

Анализ проведён на языке Python 3 с использованием только стандартной библиотеки (`csv`, `collections`). Внешние зависимости не применялись.

Воспроизводимые шаги:
1. Чтение `students.csv` через `csv.DictReader` с кодировкой `utf-8-sig`.
2. Группировка событий по `ProcessInstanceId` и сортировка внутри каждой группы по `EventIndex` — это восстанавливает хронологический порядок действий в каждом экземпляре.
3. Для каждого процесса извлекается последовательность `ActivityName` — полный маршрут (Variant).
4. Агрегация частот маршрутов даёт таблицу вариантов; агрегация пар смежных активностей — таблицу переходов.
5. Логика ветвлений восстанавливается по полю `Result` (accept / reject / return / cancel).
6. Схема визуализирована в нотации Mermaid (код прилагается в `mermaid_code.txt`).

Скрипт `process_discovery.py` запускается командой `python process_discovery.py` и генерирует все артефакты.

## 2. Обнаруженные активности, начала и окончания

**Начало.** Все 1000 экземпляров начинаются с события `Регистрация заявки` (EventType: `process_started`, Role: `system`). Это автоматическая граница процесса.

**Конец.** Все экземпляры завершены (EventType: `process_completed`) одним из трёх исходов:
- `Заявка выполнена` (Result: `fulfilled`) — успешное завершение;
- `Заявка отклонена` (Result: `rejected`) — отказ;
- `Заявка отменена` (Result: `cancelled`) — отмена инициатором.

**Основные активности** (встречаются в большинстве маршрутов): `Первичная проверка`, `Согласование руководителем`, `Проверка бюджета`, `Исполнение закупки`.

**Дополнительные активности:** `Доработка заявки` (появляется только после возврата), `Дополнительное согласование` (альтернативная ветка после бюджета).

## 3. Логика процесса: основной маршрут, развилки и возвраты

На основе частот переходов и значений поля `Result` восстановлена следующая логика:

**Шаг 1.** После `Регистрация заявки` всегда следует `Первичная проверка` (1000 переходов из 1000).
- `Result = reject` (45 случаев) → `Заявка отклонена`.
- `Result = accept` (955 случаев) → переход к руководителю.

**Шаг 2.** `Согласование руководителем` — ключевая развилка с четырьмя исходами:
- `Result = return` (174 случая) → создаётся задача `Доработка заявки`, после которой процесс **возвращается** на `Первичная проверка`. Это наблюдаемый цикл.
- `Result = cancel` (26 случаев) → `Заявка отменена`.
- `Result = reject` (18 случаев) → `Заявка отклонена`.
- `Result = accept` (911 случаев) → переход к `Проверка бюджета`.

**Шаг 3.** `Проверка бюджета` — развилка с двумя ветками (все с `Result = accept`):
- **Основной путь** (702 случая, 77%): прямой переход к `Исполнение закупки`.
- **Альтернативный путь** (209 случаев, 23%): переход через `Дополнительное согласование`, которое затем также ведёт к `Исполнение закупки`.

**Шаг 4.** `Исполнение закупки` (всегда `Result = accept`) → `Заявка выполнена`.

## 4. Подтверждение выводами из данных

**Баланс переходов.** Сумма всех выходов из `Согласование руководителем`: 174 (return) + 26 (cancel) + 18 (reject) + 911 (accept) = **1129**, что точно равно сумме входов на этот этап (955 первичных + 174 возврата). Аналогично для `Проверка бюджета`: 702 + 209 = **911** = количество входов. Это подтверждает, что модель не теряет и не дублирует переходы.

**Полное покрытие вариантов.** Выявлено ровно **8 уникальных маршрутов (Variant)**, которые в сумме покрывают **1000 из 1000 процессов (100%)**. Детальная таблица с частотами и долями приведена в `variants.csv`.

**Таблица переходов.** Выявлено **12 уникальных пар** (SourceActivity → TargetActivity), приведённых в `student_transitions.csv`. Каждая пара подтверждается конкретным числом наблюдений в журнале.

**Примеры идентификаторов:**
- Типовой маршрут без отклонений: `2fcc6cf4-603b-5153-b1f6-80db32e6b362` (Регистрация → Первичная проверка → Согласование руководителем → Проверка бюджета → Исполнение закупки → Заявка выполнена).
- Маршрут с возвратом: `64296b80-7009-5a4f-a6a9-3f9a58133200` (после `return` на этапе руководителя идёт `Доработка заявки` и возврат на `Первичная проверка`).
- Маршрут с дополнительным согласованием: `78f343a1-28d8-5473-b013-17207d09ffa8`.
- Раннее отклонение: `c7f440c6-2f22-531e-9053-ae0d7a89b19b` (отклонение уже на первичной проверке).

## 5. Границы модели и гипотезы

**Наблюдаемые факты.** Мы видим только завершённые задачи (`task_completed`) и границы процесса. Момент `task_created` в журнале отсутствует, поэтому длительность ожидания между этапами в этой модели не анализируется. Повторное выполнение одной и той же активности (например, `Первичная проверка` после возврата) зафиксировано как отдельное событие с новым `TaskId` — это корректно отражено в маршрутах.

**Гипотезы.** Поле `Amount` присутствует в журнале, но явного порога, разделяющего маршруты с `Дополнительным согласованием` и без него, в данных не обнаружено: этот этап встречается при разных суммах. Возможно, условие ветвления зависит от атрибутов, не представленных в выгрузке (категория закупки, контрагент и т.п.), либо решение принимается вручную.

**Ограничения.** Модель описывает наблюдаемое поведение, а не внутреннее устройство системы. Наличие одного порядка событий не доказывает единственно возможную схему — например, теоретически `Дополнительное согласование` может быть необязательным ручным действием, а не автоматическим правилом.

## 6. Использование AI

Языковая модель (Qwen) использовалась для написания скрипта агрегации данных на Python и формулирования структуры отчёта. Все логические выводы — проценты, баланс переходов, наличие циклов и развилок — были перепроверены прямым запросом к сырым данным (`students.csv`) и подтверждены математически. Никакие ответы модели не включены в отчёт без проверки на исходных данных.
